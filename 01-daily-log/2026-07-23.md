### 2.4 编写 Fluent 体素覆盖率诊断程序

为解释 FLUKA 完整计分功率与 Fluent 网格映射功率之间的差异，新增：

```text
fluka_to_c_translation/udf/
└── beam_1mrad_offset_2mm_coverage_diagnostic.c
```

该程序的目标不是继续求解温度场，而是遍历 Fluent 全部单元，统计每个 FLUKA 体素在 Fluent 网格中的实际覆盖情况。

主要逻辑：

```text
遍历 Fluent cell
→ 读取 cell centroid
→ 将米转换为厘米
→ 判断单元中心是否位于 FLUKA 计分盒
→ 映射到 ix、iy、iz
→ 累加该体素对应的 Fluent 单元体积
→ 计算该体素的映射功率
→ 与 FLUKA 体素理论功率比较
```

计划输出：

```text
每个体素的索引与中心坐标
原始热沉积数值
理论体素功率
映射到该体素的 Fluent 单元数量
实际覆盖体积
实际映射功率
功率恢复比例
功率差值
```

同时统计体素类别：

```text
未覆盖体素
覆盖不足体素
体积基本匹配体素
过度覆盖体素
```

这样可以进一步判断 `18.43%` 功率差异究竟来自：

* Fluent 几何并未覆盖全部 FLUKA 计分盒；
* 冷却孔道、空腔或几何外区域；
* 非结构网格与规则体素之间的体积差异；
* 单元中心采样方法的固有误差；
* 坐标原点、方向或范围设置问题。

* 删除失败构建产生的旧动态库目录；
* 使用 Fluent 内置编译器重新构建；

最终完成：

* C 文件编译；
* 目标文件生成；

## 6. 今日反思

### 6.1 独立验证可以推翻“看起来合理”的旧结论

昨日计算能够运行，温度和功率数值也处于看似合理的范围，但今天的独立数据校验表明，原先使用的 `40.37 kW` 参考值并不属于当前工况。

这说明：

> 计算能够运行、结果看起来合理，不代表数据身份和物理含义一定正确。

后续必须坚持：

```text
原始数据
→ 自动解析
→ 独立验证
→ 文件身份核验
→ 物理解释
```

不能只依赖人工观察或历史记录。

### 6.2 编译问题和物理问题必须分开处理

今天覆盖率诊断程序的兼容性调试耗时较长。源码编码、头文件路径、函数接口和串并行宏都属于软件接口问题，而体素覆盖和功率恢复属于物理映射问题。

后续应采用更严格的分层测试：

```text
最小文件能否编译
→ 数组能否链接
→ UDF 能否加载
→ cell 能否遍历
→ 坐标能否读取
→ 体素能否映射
→ 功率是否守恒
```

避免多个问题同时进入同一次构建。

### 6.3 组会材料必须区分成果与边界

本次 PPT 不以“得到一个温度结果”为中心，而是强调：

* 已恢复什么；
* 已验证什么；
* 哪些假设仍未确认；
* 下一步如何形成证据。

这种表达比单纯展示云图或迭代次数更符合工程计算的要求。
