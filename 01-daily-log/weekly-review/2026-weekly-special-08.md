# 第8篇周报·特别周刊：技术路线与工程管理

> **性质：** 非日志型周报，不对应某一自然周，不受时间范围限制。  
> **用途：** 作为8周实习周报体系中的第8篇材料，从技术主线、仓库管理与工程方法三个角度总结整个实习的组织方式。

## 本期主题

本次实习虽然由 Ansys/Fluent 学习起步，但后续逐步形成了一条较完整的粒子输运—热工耦合工程链：

```text
论文与既有工程基线
→ FLUKA 能量沉积数据
→ Python / C / UDF 接口
→ Fluent 热源加载与功率验证
→ CAD / SpaceClaim / Fluent Meshing
→ 流体域与体网格
→ Solver 温度场
→ Mechanical 热应力
```

实习阶段真正完成闭环的部分，主要包括旧 FLUKA→Fluent 热源链恢复、功率/映射诊断，以及新 `fort.30` 原始二进制数据直读与 5 mA 归一化。新版正式几何则推进到 Share Topology 主故障定位，后续仍需完成 Capping、流体 Region、Volume Mesh 和新 Cell Zone 上的正式热源挂接。

## GitHub 仓库管理

仓库并非单纯存放文件，而是承担工程追踪和交接功能。当前结构按用途分为：

- `00-admin/`：任务、规则与交接；
- `01-daily-log/`：每日事实日志及周报；
- `02-meetings/`：组会记录；
- `03-notes/`、`04-literature/`：理论与文献；
- `05-software/`：软件学习；
- `06-cases/`：算例与验证；
- `07-reports/`：阶段总结和报告；
- `08-presentation/`：汇报材料；
- `09-archive/`：历史资料；
- `fluka_to_c_translation/`：可执行的数据转换与 UDF 代码。

记录原则始终是：聊天解决即时问题，GitHub 保存需要长期追踪、复用、提交或交接的内容；区分“已阅读、已运行、已验证、待核实”，避免把推测写成事实。

## 工程方法上的变化

实习初期的工作方式更接近“遇到报错—修改参数—重新尝试”。随着任务深入，逐步转向：

```text
定义问题
→ 保存基线
→ 分离变量
→ 独立诊断
→ 守恒/数量校验
→ 健康对照
→ A/B 修改
→ 回归验证
```

例如，旧模型中不再只看温度结果，而是区分完整 FLUKA 功率、诊断映射功率和 Fluent 实际加载功率；新几何排障中也不再盲目加密网格，而是用 TUI 将 inter-zone intersection、self-intersection 和 duplicate 分开检查，并通过删除问题管路完成 A/B 验证。

## 阶段认识

本次实习最终形成的成果不只是若干软件操作或计算数值，而是一套可追溯的工程工作流：上游数据有来源，中间转换有校验，模型修改有基线，异常判断有证据，未完成项有明确边界。

因此，本篇不记录某一周“做了什么”，而是回答另一个问题：

> **这8周的工作为什么能够被继续接手，而不需要下一位重新从头考古？**

答案正是：技术路线被串联起来，关键判断被验证，文件与日志被结构化归档，当前停点与下一步已经明确。
