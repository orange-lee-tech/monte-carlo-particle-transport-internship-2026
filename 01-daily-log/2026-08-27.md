## 二、新版几何导入与初始 Share 失败

新版模型重新导入 Fluent Meshing 后，初始几何统计为：

- Body：`19`
- Face：`364`
- Edge：`509`
- Surface Mesh 后：
  - Boundary nodes：约 `1.74 million`
  - Boundary faces：约 `3.40 million`
  - Boundary face zones：`38`

Surface Mesh 本身能够正常完成，但 Share Topology 过程中出现大量：

```text
Warning: Dihedral limit violations or self-intersections found, undoing join.
```

随后进一步出现：

```text
non-manifold configuration
node insertion failed
Mesh topology corrupted (v-m-v-w)
SIGSEGV(segmentation violation)
```

尤其在约以下两簇坐标附近多次出现 non-manifold / node insertion failure：

```text
(-0.192,  0.144, 0.037)
( 0.192, -0.116, 0.095)
```

这说明问题已经不是普通的“某个 Join 没成功”，而是局部接口在 Join/Remesh 后能够直接诱发非法拓扑，必须先定位几何根因，不能继续依靠参数反复试错。

## 三、诊断前先消除网格参数漂移

检查 Guided Workflow 时发现，当时 GUI 中曾出现：

- Minimum Size：`0.0005 m`
- Curvature Normal Angle：`18°`

这与此前历史验证得到的基线不一致。此前已经证明：

- `0.5 mm` 局部/最小尺寸会使复杂接口的 Share 结果恶化；
- 当前更稳妥的基线应保持：
  - Face Size：`0.001 m`
  - Minimum Size：`0.001 m`
  - Growth Rate：`1.2`
  - Size Function：`Curvature & Proximity`
  - Curvature Normal Angle：`12°`
  - Cells Per Gap：`1`
  - Feature Angle：`40°`

因此后续诊断坚持先消除网格参数这个变量，再判断 CAD 本身。

## 五、关键接口 78 ↔ 77 的非破坏性诊断

首先检查 `zone----- ↔ wall.6`。

### 5.1 inter-zone face intersection

执行：

```text
/boundary/mark-face-intersection
(78 77)
```

得到：

```text
Total = 69515
ID 78 = 34371
ID 77 = 35144
```

两侧数量近似对称。

### 5.2 self-intersection

执行：

```scheme
(tgapi-util-mark-self-intersecting-faces '(78 77) #t)
```

结果：

```text
0
```

### 5.3 duplicate faces

执行：

```scheme
(tgapi-util-mark-duplicate-faces '(78 77))
```

结果：

```text
0
```

### 5.4 Join 候选区域

执行：

```text
/boundary/remesh/mark-join-faces
```

选择：

```text
Mark: (78)
With: (77)
Tolerance: 0.05
```

得到：

```text
Total = 71980
ID 78 = 35562
ID 77 = 36418
```

由此得到非常关键的判断：

> 单个 Surface Mesh 自身没有 self-intersection，也没有 duplicate faces；但两独立 zone 之间存在约 7 万级的真实几何相交/重合面，并且约 96% 的 Join 候选面本身就已经属于 inter-zone intersection。

因此不能再把故障归因于“Surface Mesh 自己生成坏了”，问题主要发生在两个 CAD 实体的接口关系上。

## 六、邻近接口 A/B 对照进一步锁定局部问题

为判断 `wall.6` 是否只是整个模型普遍存在的正常接触，对相邻类似对象继续做对照。

### 6.1 `78 ↔ 76 (wall.5)`


得到：


同样为大面积、近似对称的 inter-zone intersection。

### 6.2 `78 ↔ 63 (wall.7)`

执行同样检查：


结果：


这一组结果极其重要，因为它提供了同模型、同参数下的“健康对照”：

> `wall.5 / wall.6` 与主体存在几万级 inter-zone intersection，而 `wall.7` 为 0。  
> 这说明问题不是全局网格参数或 Fluent 普遍误判，而是至少集中在特定管路/接口几何上。

## 七、图形化标记进一步确认问题呈连续接触带分布

通过：

```text
/display/set/colors/highlight-color
red

/display/set-grid/marked? yes
```

并在 GUI 中只显示 `wall.5 + zone-----`，将 `78 ↔ 76` 的约 7.98 万个 intersection faces 高亮显示。

图形观察显示，问题面并不是零散随机坏三角形，而沿管—主体相关接触位置形成明显的连续带状/环状区域。

因此可向建模人员给出更准确的工程反馈：

> 新 `.x_t` 可以正常导入，Surface Mesh 单体表面自身也没有 self-intersection；真正异常是局部管—主体接口存在大面积几何相交/重合。其物理原因可能是实体体积穿模，也可能是共面重合但没有形成干净公共拓扑。仅靠 Fluent Share/Remesh 无法可靠修复。

若在 SolidWorks/SpaceClaim 中继续检查，最优先应做：

- Interference Detection / 干涉检查；
- coincidence / 共面重合检查；
- invalid face / invalid edge / short edge 检查。

## 八、删除可疑管路后的 A/B 验证

为验证“问题是否由该局部管路主导”，对模型做了一个非常直接的 A/B 对照：

> 删除当前已经定位为异常接触源的可疑管路，其他工作流尽量保持不变，再重新生成 Surface Mesh 并执行 Share Topology。

删除后模型统计变为：

- Body：`18`
- Face：`344`
- Edge：`487`
- Surface Mesh：
  - Boundary nodes：约 `1.95 million`
  - Boundary faces：约 `3.82 million`
  - Boundary face zones：`36`

Share 过程中仍能看到少量：

```text
Dihedral limit violations or self-intersections found, undoing join.
```

但与此前不同的是，Fluent 能继续完成多轮 Join/Intersect，并最终进入：

```text
Intersecting...
Done.

computing regions...
done
```

没有再次出现此前那种导致整个流程中断的：

```text
Mesh topology corrupted
SIGSEGV
```

因此可以形成当前最有说服力的 A/B 结论：

> **删除可疑管路后 Share Topology 能够实质通过，而保留该管路时会稳定诱发 non-manifold、node insertion failed、mesh topology corrupted。由此可认为该管路或其与主体的接口是此前共享拓扑失败的主导故障源。**

严格来说，删除一个实体也会改变邻近拓扑，因此不能数学上证明“只有这一处问题”；但作为工程排障证据已经足够强。

## 十、长细管“被截断/封死”的新问题定位

Share 通过后，在进入：

`封闭流体区域（封盖）`

时发现结构图中原本存在的长细管，在 Fluent 显示中看起来只剩靠近主体的一小段，且端口呈封死状态。

首先检查是否为 CAD/Surface Mesh 阶段真的丢失长管。

Surface Mesh 日志中的 Bounding Box 仍为：

```text
z_min ≈ -2.713045 m
```

这与原结构图中两根两米多长的长细管尺度相符。

因此可以排除：

- `.x_t` 导入阶段删除了整根长管；
- Surface Mesh 阶段直接把长管截没了。

真正异常发生在 Share 后的 Capping/Zone 选择阶段。

终端明确报错：

```text
Error: Enclose Fluid Regions (Capping):
The previously selected zones (zone------1.1)
could not be detected using bounding box information.
Check the selections and correct them manually.
```

同时 Fluent 给出：

```text
Due to the size of the model, faces of bodies were not automatically separated for capping and/or size assignment.
To separate out zones, set 'Invoke Zone Separation by Angle?' to 'yes'.
```

由此当前判断为：

> 删除管路、重新 Surface Mesh 和 Share 后，Face Zone 身份发生了重新编号/分裂，而旧的 `velo-inlet_1` 或 Capping 任务仍保存原先的 zone 选择。原 zone 已不存在，因此 Fluent 无法自动重新识别真实的长管开口，导致封盖任务失效，视觉上表现为“管子被截断、口子被堵死”。

这属于工作流对象失效，而不是当前证据下的 CAD 长管真实丢失。

下一步应：

1. 重新执行 `/boundary/manage/list`；
2. 找出当前两根长管实际对应的新 Face Zone；
3. 单独显示这些 zone 验证长管连续存在；
4. 在 Surface Mesh 高级选项中启用 `Invoke Zone Separation by Angle = yes`（若需要重新网格）；
5. 删除/更新旧 Capping 选择；
6. 手工重新选择真实入口/出口端面。

## 十一、主线正式回归：从几何排障返回 FLUKA→Fluent 热源加载

随着 Share Topology 的主导故障源被定位，后续不再继续无止境地围绕 Join 参数试错，而应回到此前已经建立的计算主线。

历史上已跑通的数据链为：

```text
FLUKA .29
→ Python 转换
→ heat_deposition.c / .h
→ beam_1mrad_offset_2mm_source_udf.c
→ 编译 libudf1
→ 加载 ENERGY_PLAN
→ 挂接到铜质热源 Cell Zone
→ 功率积分诊断
→ Fluent 求解
```

此前 `1 mrad + 2 mm` 工况的旧模型基线曾得到：

- FLUKA 完整计分盒功率：约 `46.7998 kW`
- zones 8–11 诊断映射功率：约 `38.1783 kW`
- 旧模型中实际加载于铜质 source 区的功率：约 `37.2432 kW`
- 完整盒与 zones 8–11 映射的净功率缺口：约 `18.422%`

逐体素诊断已经证明，该缺口主要来自：

- Fluent 实际几何与 FLUKA 规则计分盒并不完全重合；
- 单元质心映射会造成体素欠填充/过填充；
- 并非简单的“18% 单元漏映射”。

这些数值只能作为旧模型的回归基线，不能直接复制到新版正式几何。

对于新版模型，体网格完成以后必须重新完成：

1. 识别新版铜质准直器对应的 Cell Zone；
2. 不沿用旧 `zone 10 = source` 的编号假设；
3. 重新编译/加载现有 UDF；
4. 将 `ENERGY_PLAN` 挂接到新铜体 Cell Zone；
5. 重新做功率积分；
6. 再进入正式求解。
