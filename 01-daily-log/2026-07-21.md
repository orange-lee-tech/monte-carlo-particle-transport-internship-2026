## 3. 对 `.h`、`.c` 和 Fluent UDF 关系的认识

今天进一步明确了 `.h`、`.c`、UDF、`.cas` 和 `.dat` 之间的关系。

```text
FLUKA .29
→ Python转换程序
→ 能量沉积数组 .h/.c
→ Fluent UDF源程序
→ 编译生成libudf
→ 在Fluent中挂接能量源项
→ 保存.cas并进行计算
→ 生成.dat结果文件
```

其中：

* `.29` 是 FLUKA 输出的空间能量沉积数据；
* `.h` 用于声明数组及相关网格参数；
* `.c` 用于定义实际的三维数组数据；
* Fluent UDF 源程序负责读取单元中心坐标、查找对应网格数据并返回能量源项；
* `.cas` 保存网格、模型、边界条件和 UDF 挂接关系；
* `.dat` 保存温度、速度、压力等求解结果；
* `.cas` 和 `.dat` 不会直接读取 `.h` 或数据 `.c`，而是通过编译后的 `libudf` 调用相关程序。

因此，目前生成的 `.h/.c` 属于 Fluent UDF 的数据层，还不是完整可运行的 UDF。

## 5. 当前尚未完成的问题

虽然数据转换接口已经完成初步重构，但要真正用于 Fluent 计算，还需要继续解决以下问题：

1. 确认 FLUKA 坐标系与 Fluent 模型坐标系的原点和方向；
2. 将 FLUKA 使用的厘米单位与 Fluent 模型使用的米或毫米统一；
3. 确认数组下标与 Fluent 单元空间位置之间的映射关系；
4. 明确 FLUKA 输出数值的物理单位和归一化方式；
5. 根据束流功率或粒子数率，将能量沉积结果换算为 Fluent 所需的体积热源，通常单位为 `W/m³`；
6. 编写包含 `DEFINE_SOURCE` 的 Fluent UDF 源程序；
7. 在安装 Ansys 的主力机上完成 UDF 编译、加载和挂接测试。

因此，目前不能直接认为这些 `.c/.h` 文件已经能够使 Ansys 成功运行，它们只是完整计算链中的数据接口部分。

## 6. 今日收获

今天的工作不只是修改文件夹名称，而是初步建立了一套可重复、可检查的数据转换流程：

```text
原始数据保留
→ 自动转换
→ 严格校验
→ 接口声明
→ 数据定义
→ 后续UDF调用
```

相比原程序直接输出单个裸 `.c` 文件，当前结构更加清晰，也更适合后续维护和不同束流工况之间的切换。

同时认识到，粒子输运结果进入热工计算并不是简单的文件格式转换问题，还涉及坐标映射、单位换算、功率归一化和计算软件接口等多个环节。任何一个环节处理错误，都可能导致热源位置、热源强度或温度结果出现明显偏差。
