- `source` 材料为 copper；
- `wall-source` 只是该固体区域的壁面边界，不能代替体积热源挂接区域；

因此，问题不是“重新建一个 Fluent 模型”，而是“恢复原模型与 FLUKA 热源之间的接口”。

## 3. `.29`、数组 `.c/.h` 与 UDF 主程序的关系

今天对这条数据链的认识从操作层面上升到了结构层面。

### 3.1 `.29` 文件

`.29` 是 FLUKA USRBIN 等计分结果的文本输出，包含：

- 计分对象；
- X、Y、Z 范围；
- 网格数；
- 数据排列顺序；
- 每个体素的热沉积数值。

本次 `.29` 数据区共有 11200 个数。

### 3.2 热沉积数组 `.c`

```text
beam_1mrad_offset_2mm_heat_deposition.c
```

该文件负责真正保存 11200 个热沉积数值，并将 FLUKA 的一维输出顺序组织为 C 语言三维数组：

```c
array[ix][iy][iz]
```

它的目标是改变数据的存储格式和访问方式，而不是改变物理数值。

### 3.3 热沉积数组 `.h`

```text
beam_1mrad_offset_2mm_heat_deposition.h
```

该文件主要保存：

- `NX=20`、`NY=20`、`NZ=28`；
- X/Y/Z 坐标范围；
- 数组类型和数组外部声明；
- Fluent UDF 编译需要的接口声明。

`.h` 不承担主要热沉积数据存储，而是告诉其他 C 文件：数组叫什么、尺寸是多少、如何引用。

### 3.4 UDF 主程序 `.c`

```text
beam_1mrad_offset_2mm_source_udf.c
```

该文件才是 Fluent 与热沉积数组之间的物理接口，负责：

```text
读取 Fluent 单元中心坐标
→ 坐标单位转换
→ 找到对应 FLUKA 体素
→ 读取数组值
→ 完成功率单位和束流强度换算
→ 向 Fluent 返回 W/m³ 体积热源
```

因此三者分工为：

```text
.29        原始物理数据来源
数组.c     数值本体及三维存储结构
数组.h     尺寸、范围和数组声明
UDF.c      坐标映射、单位换算和 Fluent 源项接口
```

需要特别说明：当前设计意图是“`.29 → 数组.c/.h` 只做架构调整、内容不变”，但这一点还需要通过逐项自动比对来严格证明，不能仅凭脚本运行成功就默认成立。

## 4. 第一阶段：建立最小可编译 UDF

为避免一开始同时处理坐标映射、单位换算和归一化，先建立最小测试文件：

```text
beam_1mrad_offset_2mm_source_udf.c
```

测试函数使用 `DEFINE_SOURCE`，返回零热源，同时强制引用热沉积数组，用于验证：

1. Fluent 能否正确找到 `.c/.h`；
2. 数组定义和头文件声明能否链接；
3. 3D 双精度并行模式能否生成 `libudf1`；
4. Fluent 能否识别自定义源项函数。

初次构建失败，报错：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte ...
```

原因是 Fluent 2021 构建脚本按 GBK 读取源码，而测试文件中包含 UTF-8 中文注释。

处理方法：

- 将 UDF 源码改为纯 ASCII；
- 检查三个源文件中不存在非 ASCII 字节；
- 删除失败生成的旧 `libudf1` 目录；
- 使用 Fluent 内置 clang 编译器重新构建。

随后编译与链接成功，生成：

```text
libudf.dll
```

并在 Fluent 中成功加载测试函数：

```text
beam_heat_source_test
```

至此证明：

```text
数据 .c/.h
→ UDF 主程序
→ 编译
→ 链接
→ Fluent 加载
```

这条软件链可行。

## 5. Fluent 与 FLUKA 坐标映射检查

在 Fluent 中对 `source` 固体区域报告单元中心坐标范围：

```text
Xmin = -99.659055 mm
Xmax =  100.0983 mm

Ymin = -99.847816 mm
Ymax =   99.878676 mm

Zmin = -132.18749 mm
Zmax =  131.7282 mm
```

FLUKA 计分网格范围：

```text
X：-100 mm ～ 100 mm
Y：-100 mm ～ 100 mm
Z：-140 mm ～ 140 mm
```

两者在范围和尺度上高度吻合，因此第一版映射采用：

```text
FLUKA X ↔ Fluent X
FLUKA Y ↔ Fluent Y
FLUKA Z ↔ Fluent Z
```

Fluent UDF 中坐标以米读取，需转换为厘米：

```text
x_cm = x_m × 100
y_cm = y_m × 100
z_cm = z_m × 100
```

每个 FLUKA 体素边长均为 1 cm，体素索引按坐标范围计算，并加入：

- 计分盒范围检查；
- 数组上下界检查；
- 超出范围时返回零热源。

当前采用单元中心取样，即一个 Fluent 单元由其中心点落入的 FLUKA 体素决定热源值。这种方法简单、可运行，但不是严格守恒的体积交叠映射。

## 6. `.29` 数据解析与统计检查

检查 `.29` 文件头，确认：

- 总跟踪粒子数：`1.0×10^6`；
- 计分网格：`20×20×28`；
- 每个体素：`1 cm³`；
- 数据排列为矩阵 `A(ix,iy,iz)`；
- 数据区应有 11200 个数。

最初直接使用正则表达式扫描整个文件时得到 11206 个数字。原因是将格式说明：

```text
format (1(5x,1p,10(1x,e11.4)))
```

中的 6 个数字误读为热沉积数据。

修正为从 `Data follow in a matrix` 下一行开始读取后，得到：

```text
count = 11200
sum   = 0.00807373012674354
max   = 6.3796e-05
min   = 0.0
```

这一步说明数据数量与网格维数一致，也暴露出数据转换程序必须明确区分文件头和数据区，不能依赖“全文件抓数字”的脆弱做法。

## 7. 功率单位换算与当前假设

第一版 UDF 暂按 5 mA 质子束流进行换算：

```text
q''' = FLUKA数组值 × 5.0×10^12 W/m³
```

由数组统计得到：

```text
FLUKA完整计分盒参考总功率 ≈ 40.36865 kW
峰值体积热源 ≈ 3.19×10^8 W/m³
```

当前需要保持谨慎：

- 5 mA 来自当前对 CiADS 满功率工况的理解；
- 还需要结合原始 FLUKA 输入、旧 UDF、论文具体工况或课题组资料独立核实；
- 不能因为温度结果“看起来合理”就反向确认单位和束流强度一定正确。

单位换算、束流强度和空间映射都位于 UDF 主程序中，它们是最可能改变物理意义的部分，也是后续验证重点。

## 9. 热源功率诊断

仅看到函数成功挂接不能证明热源真实生效，因此增加 `DEFINE_ON_DEMAND` 诊断函数，在 Fluent 网格上遍历单元并积分：

```text
单元体积热源 W/m³ × 单元体积 m³
```

### 9.1 source 铜区加载功率

```text
source 区域：37239.7382813 W
```

### 9.2 全部单元区域诊断

```text
zone 8  fluid  =   579.189 W
zone 9  pbk    =    32.081 W
zone 10 source = 37239.738 W
zone 11 solid  =   323.883 W
总计           = 38174.891 W
```

相对于 FLUKA 完整计分盒约 40.369 kW：

```text
source 铜区加载比例：约 92.25%
Fluent 四个单元区域合计恢复：约 94.57%
当前未恢复：约 5.43%，即约 2.19 kW
```

当前没有强行乘补偿系数将结果归一化到 40.369 kW，因为缺失功率可能来自：

- FLUKA 计分盒中不属于 Fluent 几何的区域；
- 冷却孔道、空腔或真空；
- 几何边界附近单元中心采样误差；
- FLUKA 规则体素与 Fluent 非结构网格之间的体积交叠误差。

在没有查清物理去向之前，直接归一化会将本不属于铜区的功率错误转移到铜区。

## 11. Case/Data 重启问题与恢复

保存并重新读取 case/data 时，曾将文件复制进 Workbench 管理目录，并使用包含多个点号的文件名，导致 Fluent 只找到 case，没有找到对应 data：

```text
File "SYS-1.dat" not found
```

此时模型出现异常温度，说明会话中 case 与 data 状态不匹配，结果不可信。

恢复方法：

- 不继续迭代；
- 不覆盖正确检查点；
- 不再向 `dssmx_files/dp0/...` 手工塞入工作文件；
- 将 case/data 放到独立工作目录；
- 使用无空格、无括号、无额外点号且基础名完全相同的文件名；
- 通过 `Read Case & Data` 成对读取。

重新读取后温度恢复到保存前数值，证明 case/data 重启成功。

这一事故说明：

> Fluent 结果复现不仅依赖模型和 UDF，也依赖文件管理、命名规则和重启流程。工程可复现性必须包括这些操作规范。

## 15. 今日反思

### 15.1 “计算收敛”不等于“物理正确”

继续迭代几百次只能进一步证明数值解稳定，不能自动证明：

- FLUKA 单位正确；
- 5 mA 工况正确；
- 数组顺序正确；
- 坐标方向正确；
- 热源功率正确；
- 冷却边界正确；
- 结果符合真实工程条件。

因此后续不能把主要时间继续消耗在盲目增加迭代步数上。

### 15.2 “复现论文”是验证手段，不是工程终点

帅文文论文需要形成完整硕士论文叙事，必然采用一定简化。实习和工程设计更关注：

- 数据接口可信；
- 功率和能量守恒；
- 边界条件来源明确；
- 模型可重启、可复现；
- 不同工况能快速适配；
- 对异常束流和实际材料状态具有扩展能力。

因此论文结果应作为回归测试锚点，而不是为了贴合论文温度而反向调参数。

### 15.3 `.c/.h` 不应长期作为黑盒

目前已理解它们的基本分工，但还不能仅凭直觉认定转换绝对无误。需要建立自动校验：

```text
重新读取生成的数组.c
→ 还原11200个数
→ 与.29逐项比较
→ 检查数量、顺序、总和、最大值和特征点
```

只有验证通过后，才能严格声明 Python 转换只改变格式和数组结构，没有改变内容。

### 15.4 从“会运行”到“会修改”暂时后置，但不能遗忘

当前优先级是完成原工作继承和物理验证，而不是立即重构全部代码。待完成继承后，再系统处理：

- 网格尺寸自动读取；
- 坐标范围自动生成；
- 束流电流参数化；
- 区域 ID 去硬编码；
- 自动输出功率和误差；
- 多 `.29` 工况自动切换；
- Fluent 版本兼容和编译文档。
