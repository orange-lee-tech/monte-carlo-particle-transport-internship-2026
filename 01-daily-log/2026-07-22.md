## 1. 今日任务

今天的核心目标不是继续阅读论文，而是接手已有 Ansys Fluent 模型，在原有 `.cas/.dat` 基础上重新补齐已经丢失的 UDF 源文件，并尝试完成以下闭环：

```text

```

本次使用的工况为：

```text
beam_1mrad_offset_2mm
```

对应热沉积数组尺寸：

```text
20 × 20 × 28 = 11200
```

## 2. 初始状态与问题识别

打开原 Fluent 工程后，控制台出现：

```text
Auto-compilation skipped. Could not find "libudf1"
or input files for creating "libudf1" library
```

这说明原 `.cas` 中仍保存着对旧 `libudf1` 的引用，但旧编译库和原始 UDF 源文件已经丢失。

进一步确认：

- 当前 Fluent 为 3D、双精度、并行模式；
- 原 case 中 `source` 固体区域曾挂接函数 `ENERGY_PLAN::libudf1`；
- `source` 区域材料为 copper；
- `wall-source` 只是该固体的壁面边界，真实体积热源应挂在 `source (solid, id=10)` 单元区域中；
- 当前仓库内已有热沉积数据 `.c/.h`，但没有完整的 `DEFINE_SOURCE` UDF 主程序。

## 3. 第一阶段：建立最小可编译 UDF

为避免一开始就同时处理坐标映射、单位换算和物理归一化，先新建最小测试文件：

```text
beam_1mrad_offset_2mm_source_udf.c
```

测试函数使用 `DEFINE_SOURCE`，但始终返回零热源，仅强制引用热沉积数组，以验证：

1. Fluent 能否找到 `.c/.h`；
2. 数组定义和头文件声明能否正确链接；
3. 3D 双精度并行 `libudf1` 能否成功生成；
4. Fluent 能否识别自定义源项函数。

初次构建失败，报错为：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte ...
```

原因是 Fluent 2021 的构建脚本按 GBK 读取源码，而测试文件含有 UTF-8 中文注释。

处理方法：

- 将 UDF 源码改为纯 ASCII；
- 删除失败生成的 `libudf1` 目录；
- 使用 Fluent 内置 clang 编译器重新构建。

随后编译与链接成功，生成：

```text
libudf.dll
```

并在 Fluent 中成功加载测试函数：

```text
beam_heat_source_test
```

这一步证明了：

```text
数据 .c/.h
→ UDF 主程序
→ 编译
→ 链接
→ Fluent 加载
```

已经可行。

## 4. Fluent 与 FLUKA 坐标映射检查

在 Fluent 中对 `source` 固体区域报告单元中心坐标范围，得到：

```text
Xmin = -99.659055 mm
Xmax =  100.0983 mm

Ymin = -99.847816 mm
Ymax =   99.878676 mm

Zmin = -132.18749 mm
Zmax =  131.7282 mm
```

FLUKA 计分网格为：

```text
X：-10 cm ～ 10 cm，20格
Y：-10 cm ～ 10 cm，20格
Z：-14 cm ～ 14 cm，28格
```

两者高度吻合，因此本次第一版映射采用：

```text
FLUKA X ↔ Fluent X
FLUKA Y ↔ Fluent Y
FLUKA Z ↔ Fluent Z
```

Fluent UDF 内部坐标按米读取，转换为厘米：

```text
x_cm = x_m × 100
y_cm = y_m × 100
z_cm = z_m × 100
```

每个 FLUKA 体素边长为 1 cm，因此索引为：

```text
ix = floor(x_cm + 10)
iy = floor(y_cm + 10)
iz = floor(z_cm + 14)
```

并加入数组越界检查。

## 5. `.29` 数据检查与功率换算

检查 `.29` 文件头，确认：

- 总跟踪粒子数：`1.0×10^6`；
- 计分网格：`20×20×28`；
- 每个体素：`1 cm³`；
- 数据区共有 11200 个数。

最初使用正则表达式直接读取时得到 11206 个数，是因为把格式说明：

```text
format (1(5x,1p,10(1x,e11.4)))
```

中的 6 个数字误当成了热沉积数据。

修正为从 `Data follow in a matrix` 下一行开始读取后，得到：

```text
count = 11200
sum   = 0.00807373012674354
max   = 6.3796e-05
min   = 0.0
```

本次第一版 UDF 暂按 5 mA 质子束流进行换算：

```text
q''' = FLUKA数组值 × 5.0×10^12 W/m³
```

由此得到：

```text
FLUKA完整计分盒参考总功率 ≈ 40.36865 kW
峰值体积热源 ≈ 3.19×10^8 W/m³
```

说明：5 mA 是当前工作假设，后续仍需结合原始工况输入、论文和旧程序进一步核实。

## 6. 第一版真实 UDF

在测试函数基础上，将 UDF 主函数改为：

```text
DEFINE_SOURCE(ENERGY_PLAN, ...)
```

其逻辑为：

```text
读取 Fluent 单元中心坐标
→ 米转换为厘米
→ 判断是否位于 FLUKA 计分盒内
→ 计算 ix、iy、iz
→ 读取 heat_deposition[ix][iy][iz]
→ 乘以功率换算系数
→ 返回 W/m³ 体积热源
```

重新编译并加载后，Fluent 成功识别：

```text
ENERGY_PLAN
```

该函数挂接到：

```text
source (solid, id=10, copper)
```

## 7. 热源功率诊断

为验证 UDF 不是“空挂接”，又增加了 `DEFINE_ON_DEMAND` 诊断函数，遍历单元并计算：

```text
单元体积热源 W/m³ × 单元体积 m³
```

### 7.1 source 铜区实际加载功率

```text
source 区域：37239.7382813 W
```

### 7.2 各单元区域诊断

```text
zone 8  fluid  =   579.189 W
zone 9  pbk    =    32.081 W
zone 10 source = 37239.738 W
zone 11 solid  =   323.883 W
总计           = 38174.891 W
```

相对于 FLUKA 完整计分盒约 40.369 kW：

- source 铜区获得约 92.25%；
- Fluent 全部四个单元区域合计获得约 94.57%；
- 仍有约 5.43% 未通过当前单元中心采样恢复。

当前映射方法为：

```text
Fluent 单元中心
→ 查找所在 FLUKA 规则体素
→ 将该体素常值赋给整个 Fluent 单元
```

这不是严格的体积交叠守恒映射，因此复杂边界和孔道附近会出现功率偏差。本次未强行乘修正系数补齐总功率。

## 9. Case/Data 重启问题与恢复

保存并重新读取 case/data 时，曾将文件复制进 Workbench 管理目录，并使用含多个点的文件名，导致 Fluent 只找到 case，没有找到对应 data：

```text
File "SYS-1.dat" not found
```

此时出现异常温度，说明会话中 case 与 data 状态不匹配。

处理方法：

- 不再向 `dssmx_files/dp0/...` 手工塞入工作文件；
- 将 case/data 放到独立目录；
- 使用无空格、无括号、无额外点号且基础名完全相同的文件名；
- 重新以 `Read Case & Data` 方式读取。

重新读取后温度恢复到保存前值，证明重启成功。
