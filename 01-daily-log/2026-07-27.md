## 三、梳理现有五个 C 文件的目的

对 Fluent 机目录中的五个 `.c` 文件进行了逐一检查，明确其层级和用途。

### 1. `beam_1mrad_offset_2mm_heat_deposition.c`

该文件是由 Python 转换程序生成的三维热沉积数据数组，尺寸为：

```text
20 × 20 × 28 = 11200
```

它本身不包含 `DEFINE_SOURCE` 或 `DEFINE_ON_DEMAND`，不能单独作为 UDF 功能使用，只作为其他 UDF 的数据依赖。

### 2. `beam_1mrad_offset_2mm_coverage_diagnostic.c`

该文件属于早期覆盖统计版本，存在以下问题：

- Fluent 坐标单位为 m，而 FLUKA 网格边界单位为 cm，代码中未完成正确换算；
- 并行节点统计结果没有完整传回 Host；
- 遍历整个 Fluent 模型，不能清楚区分各个区域的贡献。

因此该版本确定为废弃版本，不再编译和使用。

### 3. `beam_1mrad_offset_2mm_coverage_diagnostic_fixed.c`

该文件只检查实际热源区 `zone 10`，统计：

- 热源区总单元数；
- 成功映射到 FLUKA box 的单元数；
- 映射到非零热沉积体素的单元数；
- 对应体积分数。

该版本已修正 m→cm 换算，并采用 Fluent 并行归约与 Node→Host 传值方式，可用于当前并行环境。

### 4. `beam_1mrad_offset_2mm_all_zone_power_coverage.c`

该文件将检查范围扩展到 zones 8–11，分别统计各区域的单元数、映射体积和映射功率，并计算：

- FLUKA 完整计分盒功率；
- zones 8–11 映射功率；
- 功率恢复率；
- 未恢复功率及比例。

### 5. `beam_1mrad_offset_2mm_voxel_balance.c`

该文件进行逐体素诊断，将 zones 8–11 中 Fluent 单元的体积按照单元质心归入对应 FLUKA 体素，并统计：

- 空体素；
- 欠填充体素；
- 近似完整体素；
- 过填充体素；
- 正缺失功率；
- 过填充补偿功率；
- 最终净功率缺口。

该文件是解释功率缺口来源的核心诊断程序。

## 八、逐体素功率缺口分解

v2 输出结果：

```text
voxel count                = 11200
one voxel volume           = 1.0E-06 m³
full-box power             = 46799.776711762 W
mapped cell-centroid power = 38178.315119990 W
signed power gap           = 8621.461591772 W
```

### 1. 体素分类

```text
empty voxels                = 1370
underfilled voxels (<99%)   = 7508
near-full voxels (99–101%)  = 1226
overfilled voxels (>101%)   = 2466
minimum positive fill       = 0.000016935
maximum fill                = 1.592696469
```

注意：空体素同时包含在欠填充体素统计中，因此部分填充但低于 99% 的体素数量为：

```text
7508 - 1370 = 6138
```

### 2. 功率分解

```text
positive missing power    = 9496.311024583 W
overfilled power          =  874.849432811 W
positive minus overfilled = 8621.461591772 W
```

满足：

```text
9496.311025 - 874.849433 = 8621.461592 W
```

功率收支完全闭合。

### 3. 空体素贡献很小

```text
power in completely empty voxels = 28.797857218 W
empty-voxel power fraction       = 0.061534 %
```

因此 18.422% 的功率缺口并不是由完全空体素主导，而主要来自大量体素的**部分体积欠填充**；与此同时，部分过填充体素又补偿了约 `0.875 kW`。

### 4. 当前映射方法的物理含义

当前算法按 Fluent 单元质心定位 FLUKA 体素，并把该 Fluent 单元的全部体积归入一个体素。若单元跨越多个 FLUKA 体素，则会产生局部欠填充或过填充，因此该方法不是严格的体积重叠守恒映射。

目前可以形成阶段性结论：

> FLUKA 完整规则计分盒与 Fluent 实际几何区域并不完全重合；同时，基于单元质心的离散映射会进一步造成逐体素欠填充和过填充。两者共同导致完整 FLUKA 盒积分功率与 Fluent 映射功率不一致。

## 九、`.29 → Python → C → Fluent` 计算链复核

今天纠正并固定了实际继承链：

```text
FLUKA 已处理结果 .29
→ Python 转换程序
→ heat_deposition.c / .h
→ Fluent DEFINE_SOURCE
→ 温度场
```

当前获得的是 `.29` 结果文件，而不是原始 `.inp` 输入文件，因此现阶段不应把获取 `.inp` 作为必要前提。

检查转换脚本后确认：

- 脚本从 `Data follow in a matrix` 后读取数据；
- 严格检查数值数量是否为 11200；
- 按 X 最快、Y 次之、Z 最慢的顺序重排为 `[x][y][z]`；
- 脚本不进行束流电流换算，也不修改热沉积数值的物理量级。

正式热源 UDF 中使用：

```c
#define BEAM_CURRENT_A 5.0e-3
#define M_TO_CM 100.0
#define FLUKA_TO_W_M3 (BEAM_CURRENT_A * 1.0e15)
```

并按单元质心完成 m→cm 坐标换算后读取三维数组。

当前可以确认：

- Python 转换阶段仅负责读取、检查和重排；
- `5 mA` 和 `1.0e15` 换算系数是在 UDF 中施加；
- `DEFINE_SOURCE` 与功率诊断使用相同映射逻辑；
- zone 10 的正式源项积分值与独立诊断结果一致到浮点误差量级。

后续仍应在技术文档中明确记录 `5 mA` 和 FLUKA 输出单位的来源，避免仅依赖代码中的硬编码常量。

## 十二、反思

今天前半段再次暴露出工作流管理的重要性：如果不明确交互机与 Fluent 机的边界、不尊重现有软件运行条件，容易在无效环境设置上浪费时间。后续应坚持：

1. 已被实验确认的软件限制不重复试错；
2. 低风险操作可批量推进；
3. 编译、加载和求解等高风险分叉点必须设置停止条件；
4. 每次诊断不仅给出结果，还要给出可复核的功率收支；
5. 区分“完整 FLUKA 计分盒功率”“诊断映射功率”和“Fluent 实际加载功率”，避免概念混用。

今天的关键进展不是得到一个新温度值，而是首次把热源数据链、区域挂接、功率积分和逐体素缺口解释闭合起来，为后续守恒映射和热应力分析建立了更可靠的工程基线。
